# SPARQ · презентации в Figma

Слайды собираются из JSON-спецификаций инструментом `sparq_slides`: дизайн-система (токены, стили, сетка, иконки, блоки, проверки) запечатана в плагине. Рисовать вручную (`sparq_run`) то, что выражается спецификацией, нельзя: это медленнее, дороже и кривее.

## Порядок работы

1. **Ситуация.** `sparq_status` → назвать пользователю открытые файлы, активный файл, что установлено. Нужный файл закрепить `sparq_use_file`. В новом файле: `sparq_setup_file {kit:"deck"}`, затем `sparq_deck_config {total, voice, logo?}` (voice: `pitch` — питч/заявка, «мы» можно; `report` — аналитика, без «вы/мы»).
2. **Вход.** Прочитать ТЗ/бриф и материалы. Если текст в ТЗ финальный — не переписывать, только сокращать по указаниям. Чего не хватает — один короткий вопрос пользователю.
3. **План.** Таблица: ключ · название · «после слайда читатель знает…» · рецепт (`references/patterns.md`) · главный визуальный жест. Ритм: 3–6 светлых слайдов, жесты не повторяются подряд.
4. **Спецификации.** По `references/dsl.md`; полные образцы — `examples/pitch-deck-accelerator.jsonl` (читать точечно через grep по ключу, не целиком). Текст с `**жирным**` для сканирования. Картинки — локальные пути.
5. **Сборка.** `sparq_slides` по 1–4 слайда. Разобрать `issues` и `lint`, исправить спецификацию, пересобрать. Цель — пустые issues.
6. **Глазами.** `figma_capture_screenshot {nodeId, scale:0.6}` каждого слайда; сомнительные детали — кадром узла `scale:1`. Пройти `references/quality.md`. Не сдавать без просмотренного скриншота.
7. **Вычитка и независимая проверка.** Скилл `sparq-editor`: каждая фраза, единообразие терминов по всей колоде. Перед сдачей — агенты `sparq-critic` и `sparq-copy-critic` параллельно, для отчёта с цифрами — `sparq-fact-checker`. Процесс и комментарии — `sparq-studio/references/workflow.md`.
8. **Сдача.** Коротко: что сделано, что осталось спорным (с вариантами), что нужно от пользователя. Экспорт — `sparq_export`.

## Принципы (кратко; детали — references/quality.md)
- Аккуратность важнее выразительности; выразительность — через один крупный жест на слайд и инфографику, а не через количество украшений.
- Каждый слайд: заголовок-утверждение или название раздела по ТЗ, ≤ 100 слов, текст ≥ 28 px, ≤ 5 пунктов по ≤ 2 строки.
- Не влезает — резать текст или делить слайд, кегль не трогать.
- Красный — акцент малой площадью; числа-герои белые; инверсная плашка — одна на слайд.
- Однородный перечень → иконки; доли/проценты → stack/donut; «N из M» → people; уровни → scale; процесс → steps; время → timeline; сравнение → table/compare.

## Комментарии пользователя
`sparq_comments` → список «слайд · элемент · текст рядом · сообщение». Для каждого: правка в спецификации → пересборка → скриншот. Комментарий-обобщение («везде», «ярко», «мало иконок») — применить ко всей колоде и проверить `sparq_audit`. Комментарии из других файлов не путать: смотреть `fileKey`.

## Чего нет в блоках
Сначала — ближайший блок из `references/dsl.md` или другой рецепт. Рисовать своё (`sparq_run {kit:"deck"}` с `K` и `D.block`) — только если пользователь прямо попросил схему, которой нет в системе; строить автолейаутом из токенов, затем `sparq_audit` и скриншот. Комментарии к готовым слайдам так не исправляются — только пересборкой спецификации.

## Ресурсы
- `references/dsl.md` — все блоки и параметры (читать перед первой спецификацией).
- `references/patterns.md` — рецепты 23 типов слайдов, отличия отчёта от питча.
- `references/quality.md` — чек-лист проверки и классы прошлых ошибок.
- `examples/pitch-deck-accelerator.jsonl` — 18 спецификаций питча (проще и легче).
- `examples/report-x5.jsonl` — 8 слайдов отчёта в стиле X5 (обложка-иллюстрация, содержание, вход в главу, хаб, зрелость, матрица, кейсы, источники) — **эталон стиля для отчётов**.
